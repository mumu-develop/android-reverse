# douyin_rev 吞吐测试报告（2026-11-22 更新）

## 一、先回答：新设备为什么抓不了作品列表

**不是 `device_id` 的问题，是 `iid/cdid`（安装身份）的信任级别。**

### 对照实验（决定性）

| device_id | iid / cdid | 作品列表 |
|---|---|---|
| config（老设备） | config | ✅ 20 条 |
| **new（新注册设备）** | **config** | ✅ **20 条** |
| config | new | ❌ 200 + 空 body |
| new | new | ❌ 200 + 空 body |

扩展到 4 台新设备：**4/4 都能出数据**（只要 iid/cdid 用 config 的）；
同一台设备换回自己的 iid → 立刻变空。

### 原因

`/api/register` 返回里带 `new_user: 1` —— 服务端把新注册的安装标成"新用户"，
作品列表接口对这类安装**静默返回 200 + 空 body**（既不报错也不返回 status_code，
很容易误判成签名失败）。评论和用户详情不受此限制（新设备可用）。

### 工程处理

```python
strategy.posts_device()   # 随机 device_id + 受信任的 iid/cdid
strategy.random_device("general")   # 详情/评论，可自由轮换
```

`spider` 按阶段选设备：`videos` → posts 档，`profile` / `comments` → general 档。

## 二、第二个根因：评论被风控时返回「拼接 JSON」

限流时服务端把两个对象拼在一起返回：

```
{ "has_more": 0,"status_code": 0,"min_cursor": 0,"comments": []}
{"log_pb":{"impr_id":"..."},"status_code":-99999,"status_msg":""}
```

第一个看着像"没有更多评论"，第二个 `-99999` 才是真实信号：**被风控了，这页不算数**。
标准 `json.loads` 遇到拼接 JSON 直接抛 `Extra data`，整页会被丢弃。

处理：
- `decode_stream()` 用 `raw_decode` 逐个解出对象
- 检测到 `-99999` → **不推进 cursor**，换一台设备重试同一页（最多 2 次）
- 仍失败才当作到底，避免死循环

## 三、吞吐实测

环境：unidbg 服务 6 实例、可用设备 7 台、Redis 本地、SQLite 落库、并发 8。

| 轮次 | 配置 | 任务 | 请求 | 条数 | 墙钟 | 条/秒 |
|---|---|---|---|---|---|---|
| 1 | video_pages=1, comment_pages=2 | 20 | 198 | 836 | 55 s（干完即空闲） | **15.2** |
| 2 | video_pages=2, comment_pages=3 | 36 | 514 | 1237 | 300 s（含空转） | 4.1 |
| 3（最终，含风控处理） | video_pages=2, comment_pages=3 | 36 | 751 | 917 | 241 s | **3.8** |

第 3 轮明细：

```
item_scraped_count      917
downloader/request_count 751
风控重试 294 次
任务：25 completed / 7 partial（被 240s 上限切断）/ 4 pending
落库：profile 32 / videos 389 / comments 496
```

### 怎么读这三个数

- **第 1 轮 15.2 条/秒**：轻配置、全是元数据（详情+作品），请求少、每页 20 条，最快。
- **第 3 轮 3.8 条/秒**：深翻评论（每视频 3 页），但**评论大面积被风控**（294 次重试），
  大量请求花在"空页 + 重试"上，所以条数/秒 掉下来。
- 结论：**吞吐瓶颈从"签名"变成了"设备级评论配额"**。

## 六、已知限制

1. **作品列表只能走受信任 iid**：新安装的 iid 需要"养熟"（服务端 new_user=0）才能独立用。
2. **评论深度上限**：单视频约 6688 条（cursor 6680），服务端限制。
3. **评论设备配额**：约 15-20 请求/窗口，超出返回 `-99999`，需要换设备或等待。

## 七、优化与效果（2026-11-22 第二轮）

针对「设备级评论配额」这个真瓶颈，做了四项优化：

| # | 优化 | 位置 | 作用 |
|---|---|---|---|
| 1 | **设备冷却调度器** | `signer/scheduler.py` | 收到 -99999 的设备进 Redis 冷却（90s 起，指数退避到 300s），选设备时跳过冷却中的；多 worker 共享同一份冷却状态 |
| 2 | **跳过 0 评论视频** | `spiders/user_spider.py` | 作品列表里 `comment_count == 0` 的视频不再发评论请求，直接跳过 |
| 3 | **多 worker** | `scripts/run_workers.py` | 1 个 dispatcher + N 个 spider 进程共享 Redis 队列与设备冷却 |
| 4 | **SQLite WAL + NORMAL** | `db/__init__.py` | 读写并行、少 fsync，落库不再是瓶颈 |
| 5 | **设备池直读 devices.jsonl** | `signer/device.py` | 新注册设备不用重启签名服务即可参与轮换（21 台 vs 6 台） |

### 优化前后对比（同样 36 个任务、video_pages=2、comment_pages=3）

| 指标 | 优化前（单 worker） | 优化后（3 worker） | 提升 |
|---|---|---|---|
| 墙钟 | 241 s | 180 s | -25% |
| 抓取条数 | 917 | **2202** | **2.4×** |
| 评论条数 | 496 | **1739** | **3.5×** |
| 风控重试/冷却 | 294 次重试 | **13 次冷却** | -96% |
| 条/秒 | 3.8 | **12.2** | **3.2×** |
| 折算每天 | ~33 万 | **~105 万** | 3.2× |
| 任务完成 | 25/36 | **36/36** | 全部完成 |

### 为什么提升来自「冷却」而不是「并发」

优化前：设备被风控后，代码随机换一台设备重试 —— 很可能会再次选中刚被封的那台，
于是同一页连续空转 2 次，消耗 quota 却拿不到数据（294 次重试）。

优化后：被封设备进冷却，选择时直接排除；换到的设备大概率是干净的，
一次就能过（13 次冷却）。**把"无效重试"变成了"有效轮换"。**

### 剩余可调项

| 项 | 现状 | 建议 |
|---|---|---|
| 设备数 | 21 台（9 台在冷却） | 继续 `/api/register` 加，每台约 +15-20 请求/窗口 |
| worker 数 | 3 | 加到 6-8（CPU 16 核，签名服务 6 实例） |
| 签名实例 | 6（`pool-size`） | 提到 12，签名并发 120/s → 240/s |
| 落库 | SQLite | 20 条/秒以上换 MySQL + 批量 upsert |
| 评论深度 | 每视频 3 页 | 按需调大，深度上限 335 页/6688 条 |

## 八、按现设备数的日均容量（持续压测）

测试条件：200 个任务、4 个 worker、22 台设备（实测 10-11 台同时在冷却）、
`video_pages=1`、`comment_pages=3`、并发 8/worker。

### 实测

```
墙钟 504 秒
条数 10,931（详情 168 + 视频 1,647 + 评论 9,116）
请求 2,000（4 个 worker 各 469/496/516/519）
风控冷却 262 次
任务 161 完成 / 7 partial / 32 待抓
```

| 指标 | 实测 | 折算每天 |
|---|---|---|
| 条数 | 21.7 条/秒 | **187 万条** |
| 评论 | 18.1 条/秒 | **156 万条** |
| 请求 | 3.97 请求/秒 | **34.3 万请求** |
| 用户 | 0.33 个/秒 | **2.9 万用户**（每人约 10 视频、54 评论） |

### 单设备效率

```
3.97 请求/秒 ÷ 22 台 ≈ 0.18 请求/秒/台 ≈ 10.8 请求/分钟/台
```

与「每台 15-20 请求/窗口 + 90-300 秒冷却」吻合：设备是**间歇式**工作，
一半时间在冷却，所以单台均值反而只有 11 请求/分钟。

### 扩容公式

```
日请求数 ≈ 设备数 × 0.18 请求/秒 × 86400
日评论数 ≈ 日请求数 × 每请求评论产出（实测约 4.5-20 条，取决于空页率）
```

| 设备数 | worker | 请求/天 | 评论/天（按实测产出） | 条/天 |
|---|---|---|---|---|
| 22（现状） | 4 | 34 万 | 156 万 | 187 万 |
| 44 | 8 | 68 万 | ~310 万 | ~370 万 |
| 88 | 16 | 137 万 | ~620 万 | ~740 万 |

> worker 与设备按 **1:5** 配比较合适（4 worker / 22 设备 ≈ 1:5.5）；
> 设备是配额来源，worker 只负责把配额跑满。

### 深抓评论时会怎样

如果把 `comment_pages` 从 3 提到 335（单视频抓到底）：

- 请求速率不变（仍受设备配额限制，约 4 请求/秒）
- 但每页都是 20 条有效评论，空页率大幅下降
- 按满产出估算：4 请求/秒 × 20 条 × 86400 ≈ **690 万条/天**（理论上限）
- 实际按 60-80% 有效页率：**400-550 万条/天**

结论：**当前 22 台设备的瓶颈是"请求配额"，不是"每页产出"。**
想提高评论总量，优先加设备，其次才是加深翻页。

## 九、只看「用户 + 视频」的日均容量（最终实测）

改为：pool-size=12，per-device-interval-ms=500（重启服务，无需改 jar）
→ 实测签名吞吐 21 次/秒（并发 20）

### 持续压测（只抓用户 + 视频，评论关闭）

条件：900 个任务、6 worker、评论关闭、每用户最多 2 页作品。
为了测「持续」能力，每 15 秒把已完成任务重置回 pending，连续跑 240 秒。

```
签名次数 5,056（240 秒）
→ 21.07 请求/秒
→ 折算 182 万请求/天
风控冷却 0 次
```

### 换算成用户 / 视频

实测每用户平均：

```
1 个详情请求 + ceil(视频数/20) 个作品页请求
平均 9-13 个视频 → 约 1.5 请求/用户
```

| 口径 | 每秒 | 每天 |

| 请求 | 21.07 | 182 万 |
| 用户（1.5 请求/人） | ~14 | **约 120 万** |

长时间跑可能触发该 iid 的配额（本次 240 秒未出现冷却，但未做小时级验证）。

按 50-60% 保守估算：

```
用户：60-70 万/天
视频：800-900 万/天
```

## 十一、新设备采集作品列表：已解决（匿名 iid）

### 排查结论

作品列表接口拒绝的不是"新设备"，而是**新安装的 iid**：

| 请求 | iid | 结果 |
|---|---|---|
| 作品列表 | 新注册 iid（new_user=1） | ❌ 200 + 空 body |
| 作品列表 | 真机 iid | ✅ 20 条 |
| 作品列表 | **iid=0（匿名）** | ✅ **20 条，100/100 成功率** |
| 用户详情 | iid=0 | ❌ user 为空 |
| 评论 | iid=0 | ✅ 正常 |

试过无效的手段：`X-Tt-Token`、`Cookie: ttwid=`、`new_user=0`、`cold_start=1`、
feed/settings/app_log 预热、注册后等 18 小时 —— 全部返空。

### 解决方案

```
作品列表：iid=0（匿名）+ 随机 device_id
用户详情：随机设备 + 自己的真实 iid
评论    ：随机设备（真实或匿名都行）
```

不再依赖单台老设备，单点风险消失。

### 验证

```
posts 压测        100/100 成功（iid=0，并发 8）
端到端（2 个任务）  profiles 2 / videos 999（TXT 974 + 爱吃火锅 25）
```

### 关于"改指纹重装能否生成新 iid"

会生成新 iid（install_id 是安装级标识），但新 iid 仍是 `new_user=1`，
作品列表**照样返空**。所以重装刷 iid 这条路走不通 —— 但已经不需要了。

## 十二、彻底解决「详情依赖真实 iid」

### 关键事实

不是"某个 iid 才能拉详情"，而是**任何真实 iid 都能拉详情**：

```
新注册设备（全新 iid）→ 详情：昵称 ✅ 粉丝 1,770,662 ✅
iid=0（匿名）        → 详情：user 为空 ❌
```

所以详情的问题不是"依赖某台老设备"，而是"必须有一个真实 iid"。
而 iid **可以随时用 /api/register 现造**（约 0.8 秒/台）。

### 实现：iid 池 + 隔离 + 自动补给

```
profile_device()
  ├─ 从设备池挑一个「iid 未被标记坏」的
  └─ 全部被标记坏 → 自动 register(3) 现造新设备 → 用新 iid

report_profile_result(iid, ok)
  └─ ok=false → Redis 标记 douyin_rev:iid:<iid>:profile_bad（TTL 6h）
```

spider 侧：详情返空 → 隔离该 iid → **换设备重试 2 次** → 仍失败才跳过详情继续抓作品。

### 验证（模拟 29 个 iid 全部被封）

```
① 把所有 iid 标记为 profile_bad
② 跑 2 个任务（TXT + 爱吃火锅，作品列表全量）
结果：
   tasks    completed / completed
   profiles TOMORROW X TOGETHER（粉丝 198 万）
            爱吃火锅（粉丝 13,856）
   videos   999 条
```

**详情、作品列表都没断。**

### 现在的三层容错

| 层 | 机制 |
|---|---|
| 详情 | iid 池 + 坏 iid 隔离 + 池空自动注册新设备（可再生） |
| 作品列表 | 匿名 iid=0；失败熔断切真机 iid；全挂降级 |
| 评论 | 任意设备，带冷却调度 |

### 关于「换指纹 + 重装刷 iid」

会生成新 iid，但**没必要**：脚本注册的 iid 本来就能拉详情，
新 iid 是否被标 `new_user=1` 只影响作品列表，而作品列表已经走匿名了。

## 十三、解耦后复测（2/3/4 worker，90 秒/轮）

条件：301 个任务、全量作品列表、评论关闭、作品列表走匿名 iid、详情走 iid 池。

| worker | 窗口 | 请求 | 用户 | 视频 | 用户/天 | 视频/天 | QPS |
|---|---|---|---|---|---|---|---|
| 2 | 91s | 603 | 215 | 3,545 | **20.4 万** | **336 万** | 6.61 |
| 3 | 89s | 827 | 299 | 4,849 | **29.0 万** | **470 万** | 9.28 |
| 4 | 90s | 821 | 299 | 5,135 | **28.6 万** | **491 万** | 9.08 |

结论：

- 与解耦前（第十节）基本一致 —— **QPS 上限仍是签名服务（21 次/秒）**，不是设备配额。
- 3/4 worker 都在 90 秒内把 301 个任务跑完，属于**任务池受限**，不是并发到顶。
- 解耦带来的收益是**稳定性**（不再依赖单个受信任 iid、iid 可自动再生），不是吞吐。
