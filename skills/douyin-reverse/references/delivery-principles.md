# 抖音专项 · 交付补充

> **通用交付原则以 `apk-reverse` 的 `references/delivery-principles.md` 为准。**
> 这里只补充抖音项目特有的量化经验，避免两份文档分叉。

## 抖音的档位校准

| 档位 | 抖音项目的实际形态 | 关键数字 |
|---|---|---|
| A. CLI | `Signer` + `Main`，一次签名 | 约 290 行，5-10 秒/次（JVM 启动） |
| B. RPC | Xposed 模块 + Sekiro | 约 230 行，5-20ms/次，单机 |
| C1. 常驻单实例 | Spring Boot 1 controller + 1 service | 约 200 行，48ms/次 |
| C2. C1 + 实例池 | 每实例一台设备身份 | 6 实例预热 39 秒；12 实例 120-150 秒 |
| C3. C2 + 注册/限流 | 加 `DeviceRegisterService` + `AdaptiveGate` | 约 900 行 |

## 抖音特有的升级触发器

| 现象 | 才允许升级 |
|---|---|
| 抓取被限流（软封禁） | C3 的自适应闸门 |
| 单台设备被抓到限额 | C2 多身份轮换（**限流按设备，换新身份能立刻恢复配额**） |
| 需要几十台设备 | C3 的 `/api/register` |

## 抖音特有的禁止事项

| 禁止 | 理由 |
|---|---|
| 为"验证可行性"直接上 12 实例 | 4 个够用；12 个白占 1.5GB 内存 + 150 秒预热 |
| 把 `probeOps` / `probeOne` / `directSign` / `ResidentBench` 留在交付物里 | 这些是开发期工具，模板已剔除（399 行版） |
| 喂真机 `.msdata` 给 unidbg | 设备绑定加密，会导致 VM 崩溃 |
| 用假 device_id 试签名 | 触发 `svc` 直接退出 |
| 想靠"纯 Python 重写"绕过仿真 | VMP + JIT，不可行 |

## 抖音验收的四层（比通用三层多一层）

| 层 | 判据 |
|---|---|
| ① 加载 | `JNI_OnLoad` OK |
| ② 初始化 | 配置验证 `true`，handle 非 0 |
| ③ 产出 | 6 个头齐全，`X-Gorgon` 以 `8404` 开头 |
| ④ **真实请求** | `status_code == 0` 且 `comments` 非空 |

只到 ③ 不算成功——实测有签名完全正确、但请求参数不全一直返回 `-99999` 的情况。

## 一句话

> 抖音项目的交付形态选择、最小化、禁止事项与通用原则一致；
> **差异只在数字**（实例数、预热时间、限流阈值），以及"验收必须多一层真实请求"。
