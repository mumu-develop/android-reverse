# 抓取调优与上限（实测数据）

这一份解决一个反复踩的问题：**为什么抓不齐、该怎么配参数、什么时候该放弃**。

## 一、两个硬上限

### 上限 1：服务端可见深度

单个视频的评论**翻不到底**，到某个 cursor 之后全部返回空页。

| 视频 total | 实际能拿到 | 覆盖率 | 断点 |
|---|---|---|---|
| 13013 | 6239 / 6021 / 7115 | 46-55% | cursor ≈ 6000-8000 |
| — | — | — | 超过后 `status_code=0` 但 `comments:[]` |

**验证方法**：拿全新设备直接请求深 cursor：

```
cursor=0     → 50 条 ✅
cursor=6000  → 50 条 ✅
cursor=9000  → 0 条  ❌
cursor=12500 → 0 条  ❌
```

**结论：50-60% 是这个视频的正常上限，不是 bug。** 不要为此反复调参。

### 上限 2：设备级速率限制（不是 IP 级）

**是按设备/身份限流**。每台设备有独立配额，用完进入冷却。

### 端到端验证（12 台设备 / 150 页）

| 配置 | 结果 |
|---|---|
| 6 台设备 / 150 页 | 120 OK + 30 被限，5655 条，31 秒，soft=6 |
| **12 台设备 / 150 页** | **148 OK + 2 深 cursor 空，7070 条，19.9 秒，soft=0** |

每台设备分到 12.5 页（< 15-20 预算）时完全不触发限流。
6 台时分到 25 页，超出预算，立刻被限。

**所以页数与设备数的配比**：

```
设备数 ≈ 页数 / 12
150 页 → 12 台
260 页 → 20 台以上
```

### 实现铁律：冷却必须按设备，不能全局

踩过的坑：把"软封"做成**全局闸门**，结果一次空响应把整个池子封住 ——
12 台全新设备跑 150 页，只发出 12 个请求，其余 138 个被本地秒拒（`GATE`）。

正确做法：

| 事件 | 正确反应 |
|---|---|
| 浅 cursor（< 2000）返回空 | **只冷却这台设备** 90 秒，换一台重试 |
| 深 cursor（≥ 2000）返回空 | 视为可见深度到底，**正常返回**，不冷却 |
| HTML `Access Denied` | 全局短暂冷却（罕见） |

### A/B 对照实验（决定性证据）

同一批请求、同一时间窗，唯一变量是设备数：

| 设备数 | 并发 | 结果 | 墙钟 | 服务端软封次数 |
|---|---|---|---|---|
| **1 台** | 20 | 15 成功 / 5 被限 | 21.4 s | **5** |
| **5 台** | 20 | **20 成功** | 4.9 s | **0** |
| **1 台** | 40 | 22 成功 / 18 被限 | 31.8 s | **23** |
| **5 台** | 40 | **39 成功 / 1 次瞬时空** | 10.9 s | **0** |

结论：

- **并发能力随设备数线性扩展**，不是出口 IP 的固定配额
- 单台设备的窗口预算约 **15-20 个请求**，超出即软封
- 5 台设备时 8 请求/台仍完全不触发限流
- 单台设备 40 并发会连续触发 23 次软封，几乎不可用

补充实验：池内 6 台设备全部冷却（`pauseMs=104s`）时，一台刚注册的新设备**一次请求就返回 20 条** ——
配额跟着设备走，不是跟 IP 走。

早先「12 台设备同时变空」的现象，是因为那 12 台都在爆发里被打过，各自被标记，不是共享 IP 配额。


## 二、两种封禁形态

| 形态 | 表现 | 处理 |
|---|---|---|
| **硬封** | 返回 HTML `Access Denied` / `X-TT-System-Error: 3` | 冷却 2-5 分钟 |
| **软封** | HTTP 200、`status_code=0`、`comments:[]` | 同上，**更坑**（看起来正常） |

**软封的判定**：`cursor=0` 也返回空 → 确定被限，不是深度问题。

## 三、推荐参数

### 抓取端

```bash
python dy-fetch-all.py <aweme_id> \
    -c 4 \        # 并发 4（不要更高）
    -r 8 \        # 全局 8 req/s 令牌桶（不是每设备）
    -m 150 \      # 最多 150 页（覆盖 ~7500 条，再往后是空页）
    --stop-empty 5
```

预期：**30-60 秒拿到 6000-7000 条**。

参数取舍：

| 想更快 | 想更稳 |
|---|---|
| `-c 8 -r 12`，容易撞限流 | `-c 2 -r 4`，慢但几乎不封 |
| 只适合短时间小批量 | 适合长期跑 |

### 服务端

```yaml
douyin.sign:
  pool-size: 6              # 6 个实例约 39 秒预热，够 4 并发
  per-device-interval-ms: 1500   # 每设备最小间隔
  cooldown-base-ms: 10000        # 检测到限流的基础冷却
  cooldown-max-ms: 120000        # 冷却上限（别设太大，会阻塞请求）
  fetch-retries: 3
```

**关键**：冷却期间**快速失败**（返回 `ok:false` + "冷却中，剩余 N 秒"），
不要阻塞 HTTP 线程。阻塞会导致客户端超时（实测 180 秒 timeout 被打满）。

## 四、客户端必须有的三个设计

### 1. 全局令牌桶（不是每设备限速）

每设备限速 + 全设备并发 = 总量仍然爆炸。

```python
class TokenBucket:
    def take(self):
        while True:
            with self.lock:
                now = time.time()
                self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
                self.last = now
                if self.tokens >= 1:
                    self.tokens -= 1
                    return
                need = (1 - self.tokens) / self.rate
            time.sleep(min(need, 0.5))
```

### 2. 提前止损

连续 N 页空/失败就停，别把剩余请求全打空页。

```python
if failed or not cs:
    empty_streak += 1
    if empty_streak >= args.stop_empty:
        stop.set()          # 取消剩余任务
        break
else:
    empty_streak = 0
```

### 3. 断点续抓

每页落盘 `out.json.parts.jsonl`，中断后 `--resume` 从断点继续。
限流环境下不可能一次跑完，续抓是必需品。

### 4. 识别"冷却中"响应，等待而不是计为空页

服务端返回 `ok:false` + `"冷却中，剩余 N 秒"` 时：

```python
if "冷却" in err:
    m = re.search(r"剩余 (\d+) 秒", err)
    time.sleep(int(m.group(1)) + 2 if m else 15)
    continue        # 重试，不计入空页
```

否则连续几次冷却会被误判成"深度到底"，提前停止。

## 五、什么时候该上代理

| 需求 | 是否够用 |
|---|---|
| 单个视频 < 8000 条评论 | 不用代理，也不用换设备 |
| 需要并发/更多配额 | **多注册几台设备**（并发能力近似线性扩展），比上代理有效 |
| 每天抓 10-20 个视频 | 单设备勉强，建议 3-5 台轮换 |
| 批量抓几百个视频 | **必须代理池** |
| 抓全量（> 8000 条） | 代理也解决不了深度上限 |

代理只解决**速率**，解决不了**深度**。

## 六、性能基准（40.2.0 实测）

### 6.1 签名吞吐（先看这个，配错了它就是天花板）

```
签名吞吐(次/秒) ≈ pool-size ÷ (per-device-interval-ms / 1000)
```

| 配置 | 实测签名吞吐 |
|---|---|
| pool-size=6，interval=1500ms | **4.2 次/秒**（并发 8 和 20 都一样 —— 就是被间隔卡住） |
| pool-size=12，interval=500ms | **21 次/秒** |
| pool-size=12，interval=500ms（并发 20） | 21.2 次/秒 |

单次签名仍然 48ms（37-68ms），但**吞吐由实例数与间隔决定**，不是由单次耗时决定。

### 6.2 单接口基准

| 指标 | 值 |
|---|---|
| 单页评论（签名+请求） | 约 230-550ms |
| 单页作品列表（20 条） | 约 1.0-1.3 秒（响应体约 500KB） |
| 用户详情（单次） | 约 0.5-0.6 秒（16-17KB，136-141 字段） |
| 每实例内存 | 约 120-150MB |
| 6 实例预热 | 39 秒 |
| 12 实例预热 | 60-90 秒 |

### 6.3 端到端容量（301 任务、全量作品翻页、评论关闭）

| worker | QPS | 用户/天 | 视频/天 |
|---|---|---|---|
| 2 | 6.6 | 20.4 万 | 336 万 |
| 3 | 9.3 | 29.0 万 | 470 万 |
| 4 | 9.1（任务池跑完） | 28.6 万 | 491 万 |

> worker : 设备 ≈ 1:5；设备是配额来源，worker 只负责把配额跑满。
> 全量翻页口径下，每个用户约 1 个详情请求 + ceil(视频数/20) 个作品页请求，实测平均 16.6 个视频/用户。

### 6.4 评论深度（未变）

| 指标 | 值 |
|---|---|
| 单视频深度上限 | 约 6688 条（cursor≈6680 处 `has_more=0`），覆盖率约 59% |
| 评论吞吐（单设备） | 约 46 条/秒（231ms/页） |

## 七、一句话结论

> **签名单次快（48ms），但吞吐 = 实例数 ÷ 间隔，配错了它才是瓶颈（6×1500ms 只有 4 次/秒）。**
> **吞吐起来后，真正的约束是：**
> **① 接口身份（详情要真实 iid、作品列表要匿名 iid=0）；**
> **② 设备级配额（每台约 15-40 请求/窗口，换设备立刻恢复）；**
> **③ 深度上限（约 6000-8000 条，与设备无关，做不到突破）。**
> **所以：要更多配额 → 加设备/加实例；要突破深度 → 做不到；代理只解决速率，解决不了深度。**
