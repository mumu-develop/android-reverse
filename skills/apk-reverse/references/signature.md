# API 签名还原

> 由 `apk-reverse` 按需引用。只在确实要还原接口签名/加密参数时读这份。

## 1. 先分类

| 类型 | 判定 | 复现 |
|---|---|---|
| **参数拼接哈希** | 签名随参数变化 | 排序 → `k=v&` 或纯值拼接 → 追加 salt → MD5/HMAC |
| **只签路径+时间戳** | 改参数签名不变 | `HMAC(key, "METHOD&urlencode(path)&ts")` → base64 |

**实测案例**：

- 豆瓣 frodo：`base64(HMAC-SHA1("bf7dddc7c9cfe6f7", "GET&%2Fapi%2Fv2%2Fhome_banner&1793457533"))`
- 达川观察：`MD5(MD5(appSign).upper() + account + token + timestamp).upper()`，其中 `appSign = MD5(证书DER小写hex).upper()`
- 海南航空：`HMAC-SHA1(SALT, 值拼接(headers) + 值拼接(query) + 值拼接(扁平body) + appSign)`，`appSign = MD5(证书DER).upper()`

判断不了就直接 hook Mac/MessageDigest 的输入输出（见 `anti-debug.md` 的 hook 章节），别猜。

## 2. 从接口到 native 的定位链

```
① 抓包拿到签名参数名（sign / _sig / hnairSign / token ...）
② jadx: search_classes_by_keyword("<参数名>", search_in="code")
③ 找到构造函数里的赋值点 → 追到工具类 → 追到 System.loadLibrary
④ 拿到 (so 名, 类名, native 方法签名)
⑤ IDA: get_function_by_name("Java_<pkg>_<Cls>_<method>") → decompile
```

要点：

- **类名可能被混淆或不符合包名直觉**，以 `RegisterNatives` 日志里的类名为准
- so 未 strip 时，C++ 类名（`HNASignature::parseParamJSON`）直接可读，比读汇编快一个数量级
- 只导出 JNI 入口、没有 crypto 符号 → 哈希多半是内联/自研，别指望 `strings SHA1_Init`

## 3. 用受控小输入反推拼接结构

比暴力猜快得多：

1. 每个入参给一个可识别的小标记：`{"a":"A1"}` / `{"q":"Q1"}` / `"S1"` / `"P1"`，调一次目标方法
2. 看返回值里哪些标记出现、以什么顺序出现 → **直接读出拼接顺序**
3. 全空输入也跑一次，拿到"内置常量"的指纹

**两个必须记住的陷阱**：

- 返回值形如 `签名>>明文>>盐` 时，**`>>` 后面通常只是 `toString()` 的调试展示，不是哈希输入**。
  照它做哈希必然全灭（实测在 20 万种组合里 0 命中，真因是少了拼在末尾的 appSign）
- 签名对象常是「`data` 平铺进 `common`」的扁平 JSON，**不是**发出去的嵌套 body。
  看到 `{"common":{...},"data":{...}}` 时先去 dex 找 `requestBodyForSign` 这类合并逻辑

## 4. 服务端回"验签失败"时，先换客户端，别改算法

症状：**字节完全一致的抓包重放，服务端仍返回 `E00001` / "验签失败" / 通用风控错误**。

分诊顺序（别倒着来）：

0. **先对照真机的完整参数集** —— 签名算法正确、但请求参数比真机少，同样会被拒。
   抓真机参数的办法：hook `org.json.JSONObject.toString()`，过滤含 `device_id=` 的连接串；
   或 hook `JSONArray.toString()` 抓初始化配置。**确认你发的参数是真机的超集。**
   典型症状：签名能复算、重放也失败、错误码是通用风控码（各家形如 `-99999` / `E00001` / `10001`）。
   实测教训：某目标签名完全正确，但只带 8 个参数、真机带 28 个 → 一直返回签名错误码。
1. **立刻重放刚抓的包**（5 分钟内），用 curl —— 能过说明请求内容没问题，是你这个客户端的问题
2. **同一份字节换客户端**：`urllib` 失败 + `curl` 成功 = **TLS/JA3 指纹被拦**
3. 只有 1、2 都通过、内容仍被拒，才回去查签名算法

实测（海南航空）：Python `urllib`/`requests` 一律 `E00001`；换 `curl_cffi` 直接过，且
`chrome`/`safari`/`firefox`/`edge`/不指定 全部都能过——拦的是"像不像正常 TLS 客户端"，不是特定指纹。

> 错误码叫"验签失败"极具误导性。判断"是不是签名错"的唯一可靠办法是**换客户端对照**，
> 不是看错误码，也不是反复改拼接顺序。

**可用的客户端**：

| 客户端 | 结果 | 备注 |
|---|---|---|
| Python `urllib` / `requests` | 常被拦 | TLS 栈特征明显 |
| `curl.exe` 子进程 | 通常可过 | 每次起进程，2~3s/条 |
| **`curl_cffi`** | 通常可过 | 进程内、连接复用，0.4~0.6s/条，**首选** |

## 5. 验证纪律

- **三重验证**才算还原完成：① 用抓包原值复算签名，逐字节一致 ② 换一组自己造的参数，服务端仍接受 ③ 与 so 实际执行结果对照（unidbg / frida）
- **别在离线复现成功就宣布完成** —— 必须真发一次请求看返回
- 时间戳有窗口期：抓包超过几分钟基本会失效，别用旧包判断"服务端拒绝"

## 6. 「被风控」还是「服务端慢」？

| 现象 | 判别 | 结论 |
|---|---|---|
| 所有客户端都 `E00001` / 通用错误 | 换 curl 重放同一份字节 | 内容问题 → 查签名 |
| 只有某个客户端失败 | 见 §4 | 客户端指纹 |
| 200 但 `success=false` + 业务错误码 | **先查错误码含义**（如 `0903` = 无航班/日期超销售期） | 业务态，不是风控 |
| **200 + 业务码 0 + 数据为空** | 换时间/换设备再请求一次；首屏也空 | **软封禁**（`200` 看起来完全正常），等 1-3 分钟 |
| 请求量突增后开始返回空 | 数一下最近 N 分钟发了多少请求 | 触发**IP 级**限流；换设备/换 device_id **无效** |
| 200 正常但 QPS 上不去 | 见下面的反推法 | 服务端并行槽位 |

**反推服务端并行度**：

```
并行度 = QPS × 单条耗时
```

1. 串行测单条耗时 T（用 `curl_cffi`，别用带进程开销的 curl 子进程）
2. 多档并发测 QPS
3. `QPS × T` 恒定在 2~4 → 服务端并行槽位受限，堆并发只增延迟、不增吞吐
4. 换 `did` / 机型复测：QPS 不变 → 不是按设备限流
5. 换出口 IP 复测：QPS 上升 → 按 IP 限流；不变 → 后端全局瓶颈

实测（海南航空）：单条 2.6s、最优并发 8、QPS 1.36，反推并行度 3.5；随机 `did`/机型无改善。

**限流维度实测**：某目标在 64 并发后，**所有**设备（含从未用过的）同时返回空 ——
限流按 **IP**，不按设备。设备轮换只解决"身份被标记"，解决不了"出口 IP 配额"。
要突破只有换出口 IP（代理池），且注意：**代理只解决速率，解决不了服务端可见深度上限**。

**AES 密文与时间无关的小陷阱**：CBC 首块 `P1 = D(C1) XOR IV`，若 IV 前 N 字节与明文前 N 字节相同，
两者抵消 → 不同时间戳的抓包里密文完全一致。别急着断定"缓存/复用"，按 IV 公式验算一遍再下结论。
