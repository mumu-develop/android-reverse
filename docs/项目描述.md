# 多目标社媒数据采集系统（协议逆向 + 采集工程）

**项目背景**：面向 Ins、TT、AMZ、YT、某X书、某X音 等社媒平台做内容与互动数据采集，交付数仓与运营分析使用；需脱离浏览器与真机，支撑多账号、批量、稳定采集。

**协议逆向**：Web 侧覆盖四类保护机制——TT 的 webmssdk 签名调用链与 X-Bogus、msToken 类浏览器环境参数；YT InnerTube 的 visitorData 与 poToken 链路，走 BotGuard challenge 与 VM 执行链路；Ins GraphQL 的 doc_id 轮换、登录态参数与请求头维护；AMZ 的会话 cookie 体系与登录协议加密字段还原。签名部分纯 Python 复现，环境依赖重的用 jsdom 补环境执行，前端加密入口结合 webpack 模块还原定位。

APP 侧面向某X书与某X音。某X书加固包经 frida-dexdump 脱壳后，用 jadx 追溯请求构造类与 native 声明，定位到 `System.loadLibrary` 与 Shield 签名入口，再由 IDA 跟进入参拼装与加密流程，最终以纯算法复现签名。某X音六神签名（X-Argus/X-Gorgon/X-Helios/X-Khronos/X-Ladon/X-Medusa）经 jadx 定位 native 入口、IDA 确认签名由 VMP 与运行时 JIT 产出，判定纯算不可行后改用 unidbg 加载 so、补齐 JNI 环境驱动初始化以还原签名，再由 Python 拼装完整请求参数、携带签名头请求接口获取数据；签名逻辑沉淀为内部签名服务接口，供采集调度批量调用。

**采集架构**：整体为"逆向产出接口/Node 服务 + 多 Scrapy 进程"的架构——逆向侧把签名与协议封装为可调用的接口或 Node 服务，采集侧多个 Scrapy 进程独立运行、互不干预，共享同一 Redis 实例。同一平台的不同采集任务按 Spider 拆分而非拆集群：每个 Spider 有唯一 name，Scrapy-Redis 按 spider name 自动隔离请求队列与去重指纹，多进程共享 Redis 但任务数据互不冲突；SCHEDULER_PERSIST 开启保证断点续爬与跨实例调度一致性，避免实例退出后调度器清空导致重复调度。业务层用 Redis 分布式锁保证目标级互斥，防止多进程对同一目标的 token/cookie 刷新等非并行操作冲突；APP 侧另设设备租借锁，同一设备身份在同一时刻仅被一个采集进程持有，规避多进程共用设备触发的服务端限流。中间件承担 UA 池、代理池按需获取与失效剔除、请求重试与响应字段解析（复用逆向产出的解密逻辑），Pipeline 分流入库；浏览器渲染仅用于登录态获取等辅助环节，不进入主采集链路。限流按设备维度建模：单设备存在请求窗口配额，超限仅冷却该设备并自动换台重试，配额与页数按"设备数 ≈ 页数/12"配比规划，避免全局降速拖累整体吞吐。反检测按检测面分层：网络层自建动态住宅代理池（每请求换 IP 并限频）+ curl_cffi 伪造 TLS/JA3 指纹，请求层随机化请求头，设备层维护真实机型画像的设备身份池并保持画像内部自洽，页面层处理反调试与前端加密入口定位。

**产出**：签名能力以接口/Node 服务形式复用，支撑多目标、多账号批量采集；采集结果按约定 schema 交付数仓清洗入库，采集侧负责去重、字段完整与失败重试。
