# 手机抓包环境排错手册

> 本文基于一次完整的排查过程整理：从"Charles 抓不到任何请求"到最终打通，
> 期间遇到 10 个问题，其中 6 个是"配了但没生效"，4 个是环境本身的坑。

---

## 一、先建立分层模型

任何"抓不到包"的问题，都可以落到下面四层中的一层。**从上往下逐层验证，不要跳层。**

```
L1  App 有没有把流量交给代理？
      ├─ 系统代理（settings put global http_proxy）
      ├─ VPN 应用（Postern / Kitsunebi 的规则）
      ├─ LSPosed 插件（hook ProxySelector / ConnectivityManager）
      └─ 都没配 → 流量直连，代理永远看不到

L2  手机能不能连到 PC 的那个端口？
      ├─ 路由（VPN 有没有把目标地址兜进隧道）
      ├─ 防火墙（Windows 入站规则、程序级 Block 规则、安全软件）
      └─ 端口占用（PC 上谁在监听）

L3  PC 上到底有没有程序在监听？
      ├─ Charles 的 HTTP 端口（默认 8888）
      ├─ Charles 的 SOCKS 端口（默认 8889，**默认不开启**）
      └─ 多个安装/多个实例导致的配置分叉

L4  HTTPS 能不能解密？
      ├─ 手机是否信任 Charles 的 CA
      ├─ 手机装的 CA == Charles 正在用的 CA 吗
      └─ App 是否有证书绑定（pinning）
```

## 二、本次遇到的 10 个问题

### L1 层：流量没交给代理（3 个）

#### 问题 1：Postern 配了代理，但 Charles 零请求

**现象**：Postern 里配好了 proxy，Charles 一条记录没有。

**根因**：Postern 的"代理（Proxy）"和"规则（Rule）"是两件事。
只配 Proxy 不配 Rule，流量默认走 `DIRECT`（直连），根本不进代理。

**判据**：`tun0` 有流量（说明 VPN 在工作），但 Charles 侧 0 连接。

**处理**：Rules 里加一条"全部流量 → PROXY"，然后断开重连 VPN。

#### 问题 2：VPN 把发往 PC 的流量也兜进隧道

**现象**：手机一直 `SYN_SENT`，PC 侧连半开连接都没有。

**判据**：
```bash
adb shell su -c "ip route get 192.168.1.22"
# → dev tun0  ← 走 VPN 了，不是 wlan0
```

**处理**：在 VPN 应用里把代理服务器地址（或整个局域网段）设为 DIRECT 绕过；
或用 `127.0.0.1` + `adb reverse`（回环不会被 VPN 捕获）。

#### 问题 3：系统代理持久化 vs `adb reverse` 不持久化

**现象**：手机重启后所有 App 报"网络错误"。

**根因**：
- `settings put global http_proxy` 写进 `/data/system/users/0/settings_global.xml`（ABX 二进制），**重启后还在**
- `adb reverse` 由 PC 侧 adb server 维护，**重启/拔线/`adb kill-server` 后消失**
- 两者叠加：手机把流量发往 `127.0.0.1:8888`，没人监听 → 全机断网

**验证持久化**：
```bash
strings /data/system/users/0/settings_global.xml | grep -A2 proxy
```

**处理**：见第五节「开机自清兜底」。

### L2 层：连不通（4 个）

#### 问题 4：`nc` 的返回值有歧义，看不出通没通

**现象**：`nc host port` 返回 0，但 Charles 没收到。

**根因**：Android 的 `toybox nc` 对**不可达**地址也会返回 0（超时后）。

**校准结果**：

| 场景 | exit | 耗时 |
|---|---|---|
| 端口开放 | 0 | **0s** |
| 端口关闭（有 RST） | 1 | **0s** |
| 被防火墙丢弃 | 1 | **3s（超时）** |
| 不可达 | 0 | 2-3s |

**正确用法：用耗时区分，不要只看 exit code。**

```sh
t0=$(date +%s)
timeout 5 toybox nc -w 3 192.168.1.22 8889 < /dev/null
rc=$?
t1=$(date +%s)
echo "exit=$rc elapsed=$((t1-t0))s"
```

#### 问题 5：防火墙规则"加了但不生效"

**现象**：8888 能通，8889 不通，两条规则配得一模一样。

**根因**：`C:\python311\python.exe` 有两条**程序级 Block** 规则。
**程序级 Block 优先于端口级 Allow**——所以 python 监听的任何端口都被拦。

```
程序: C:\python311\python.exe
Action: Block      ← 两条
```

而 `Charles.exe` 有程序级 Allow：

```
程序: ...\Charles.exe
Action: Allow      ← 程序级 Allow = 所有端口放行
```

**结论**：
- 排查"端口不通"时，**先查程序级规则，再查端口规则**
- 用跟目标程序不同的解释器做测试，会得出错误结论

**查法**：
```powershell
netsh advfirewall firewall show rule name=all dir=in verbose |
  Select-String -Pattern "Program:|Action:" -Context 0,0
```

#### 问题 6：`Get-NetFirewallRule` 查不到，`netsh` 能查到

**现象**：PowerShell cmdlet 返回空，`netsh advfirewall firewall show rule` 能看到规则。

**处理**：两个工具都试一遍，别因为一个查不到就断定"规则没加"。

```powershell
netsh advfirewall firewall show rule name=all dir=in | Select-String "8889"
```

#### 问题 7：安全软件可能接管防火墙

**现象**：规则加了、配置正确，但仍然不通。

**判据**：机器上跑着 `2345SafeCenterSvc` / `2345RTProtect` / `360huabao` 这类进程。

**处理**：临时退出安全软件再测；确认是它拦的之后，在它的设置里放行。

### L3 层：PC 没在监听（2 个）

#### 问题 8：同一个软件装了两份，配置分叉

**现象**：明明在 Charles 里开了 SOCKS 8889，但它只监听 8888。

**根因**：机器上有两个 Charles：

| 安装 | 配置目录 | SOCKS |
|---|---|---|
| `D:\charles\Charles.exe` | `%APPDATA%\Charles\charles.config` | 关闭 |
| **Microsoft Store 版** | `%LOCALAPPDATA%\Packages\XK72.Charles_dtzq29nva69ra\RoamingState\charles.config` | 开启 |

启动哪个，就用哪个的配置。**Store 版会被 AppData 重定向，配置文件不在 `%APPDATA%`。**

**判据**：
```powershell
# 看正在跑的是哪个
Get-Process Charles | Select-Object Id, Path

# 看配置里到底开没开（按实际路径查）
Select-String -Path "<实际配置路径>" -Pattern "enableSOCKSProxy|SOCKSPort"
```

**处理**：确认用哪一份，关掉另一份，并固定用同一个快捷方式启动。

#### 问题 9：端口被占用导致部分端口静默绑定失败

**现象**：配置里 SOCKS 是开的，但 Charles 只监听了 8888。

**根因**：启动时 8889 被别的进程（我的测试监听器）占着。Charles **不会报错**，只是少绑一个端口。

**处理**：
```powershell
# 先看端口占用
Get-NetTCPConnection -LocalPort 8889 -State Listen | Select OwningProcess
# 腾空后重启 Charles
Get-Process Charles | Stop-Process -Force
```

### L4 层：HTTPS 解不开（1 个）

#### 问题 10：装的是 CA，但不是 Charles 正在用的那张

**现象**：证书已装进系统、Charles 也配了 SSL Proxying，仍然解不开。

**根因**：两个 Charles 各自生成了自己的 CA：

| 证书 | 生成时间 | 归属 |
|---|---|---|
| `818e236c.0` | 17 Aug 2026 | **Store 版正在用** |
| `9ae7a7d0.0` | 19 Aug 2026 | `D:\charles` 那份 |

装错的那张对不上，客户端不认。

**判据（必须做这一步）**：
```powershell
# 1. 从"正在运行的 Charles"取它的 CA
#    Store 版路径：
$pem = "$env:LOCALAPPDATA\Packages\XK72.Charles_dtzq29nva69ra\RoamingState\data\ca\charles-proxy-ssl-proxying-certificate.pem"

# 2. 算哈希名，和手机里装的比对
openssl x509 -in $pem -noout -subject -dates -subject_hash_old
```

**Android 证书命名规则**：文件名必须等于 `subject_hash_old`，例如 `818e236c.0`。

## 三、可复用的排查决策树

```
Charles 没有请求
│
├─ 手机上 netstat 有到 PC 的 ESTABLISHED 吗？
│   │
│   ├─ 有 → 流量到了 Charles。问题在 L4（证书）或 Charles 的 SSL 设置
│   │        → 查 SSL Proxying 有没有配 *:443
│   │        → 比对 CA 是不是同一张
│   │
│   └─ 没有
│        │
│        ├─ 全是 SYN_SENT？
│        │    ├─ 包被丢弃（防火墙 / 安全软件 / 程序级 Block）
│        │    └─ 路由走 VPN 了（ip route get 目标IP）
│        │
│        └─ 连 SYN 都没有？
│             └─ App 根本没把流量交给代理 → 回 L1
│
└─ PC 上有程序监听那个端口吗？
    ├─ 没有 → Charles 没开对应端口（SOCKS 默认关闭 / 端口被占）
    └─ 有 → 继续看连接状态
```

### 判据速查

| 现象 | 含义 |
|---|---|
| 手机 `SYN_SENT` 堆积 | 包发不出去或被丢弃 |
| 连接 **3 秒超时** | 防火墙丢弃（不是拒绝） |
| 连接 **0 秒被拒** | 端口没开（正常 RST） |
| PC 侧无 `SYN_RECEIVED` | 包没到 TCP 栈 → 上游被拦 |
| PC 能连手机、手机连不上 PC | 单向拦截，查 PC 入站 |
| ICMP 通但 TCP 不通 | 三层通、四层被拦 → 防火墙 |
| `tun0` 有流量但 Charles 没连接 | VPN 规则没匹配（走 DIRECT） |

## 四、以后的标准操作顺序

### 开工前 30 秒自检

```powershell
# 1. 只有一个 Charles 在跑？
Get-Process Charles | Select-Object Id, Path

# 2. 需要的端口在监听吗？（HTTP 8888 / SOCKS 8889）
foreach ($p in 8888, 8889) {
    Get-NetTCPConnection -LocalPort $p -State Listen -ErrorAction SilentlyContinue |
        Select-Object @{n='Port';e={$p}}, OwningProcess
}

# 3. 手机侧代理状态
adb shell settings get global http_proxy
adb reverse --list
```

### 四层验证

| 层 | 验证命令 | 通过标志 |
|---|---|---|
| L1 | 手机 `netstat -tn \| grep :8889` | 有 ESTABLISHED |
| L2 | `nc` + 计时 | 0-1 秒返回 |
| L3 | `Get-NetTCPConnection -State Listen` | 进程名是 Charles |
| L4 | `openssl x509 -subject_hash_old` + 手机证书文件名 | 两者一致 |

### 收工

```powershell
.\tools\restore-proxy.ps1 -Clear
```

## 五、开机自清兜底（防断网）

**风险**：系统代理持久化，`adb reverse` 不持久化 → 重启后全机断网。

**方案**：Android 侧的守护脚本，每 20 秒检查"代理开着但端口无人监听"就自动清掉。

```sh
# /data/adb/service.d/99-proxy-guard.sh
proxy=$(settings get global http_proxy)
case "$proxy" in ""|":0") exit 0 ;; esac
host=${proxy%:*}; port=${proxy##*:}
if [ "$host" = "127.0.0.1" ]; then
    ss -tln | grep -q "127\.0\.0\.1:$port[[:space:]]" || settings put global http_proxy :0
fi
```

**为什么用 `ss` 而不是 `nc`**：`adb reverse` 会在手机侧建一个 LISTEN socket，
直接查监听表最准确；`nc` 对不可达地址会误报成功。

## 六、这次最值钱的五条认知

1. **"配了" ≠ "生效"**
   Postern 配了代理没配规则、Charles 开了 SOCKS 但端口被占、防火墙加了规则但被程序级 Block 覆盖——
   三者现象一样（没流量），原因完全不同。

2. **程序级规则优先于端口级规则**
   查防火墙不能只看端口，必须先看程序。

3. **同一个软件多份安装会让配置分叉**
   尤其是 Microsoft Store 版（AppData 被重定向）。用之前先确认 `Get-Process | Select Path`。

4. **验证工具本身可能说谎**
   `nc` 的 exit code、`Get-NetFirewallRule` 查不到、`settings get` 缓存——
   每个判据都要有第二个独立来源交叉验证。

5. **持久化状态是最大的隐患**
   系统代理、VPN 配置、证书文件都会跨重启存活，而 `adb reverse` 不会。
   任何"只在一端生效"的配置组合，重启后都可能变成故障。
