# 多目标社媒数据采集系统（协议逆向 + 采集工程）

面向 Ins、TT、AMZ、YT、某X书、某X音 六个平台的内容与互动数据采集，交付数仓与运营分析。
**核心约束：脱离浏览器与真机，支撑多账号、批量、稳定采集。**

---

## 0. 总览

### 0.1 平台与保护机制矩阵

| 平台 | 端 | 保护机制 | 攻克路线 |
|---|---|---|---|
| TT | Web | webmssdk 签名链、X-Bogus、msToken | 纯 Python + jsdom 补环境 |
| YT | Web | InnerTube visitorData、poToken、BotGuard | BotGuard challenge + VM 执行链 |
| Ins | Web | GraphQL doc_id 轮换、登录态、请求头 | 纯 Python |
| AMZ | Web | 会话 cookie 体系、登录协议加密字段 | 纯 Python |
| 某X书 | APP | 加固、`libxyass.so` Shield 签名 | unidbg 补环境 / 纯算法（按复杂度选路） |
| **某X音** | **APP** | **六神签名（VMP + JIT + 跨库组装）** | **unidbg 仿真 + 自主注册设备池** |

### 0.2 架构总览

```
┌──────────────── 逆向侧 ────────────────┐      ┌──────────── 采集侧 ────────────┐
│ Web 签名（Python / jsdom）              │      │ Scrapy 进程 × N（独立）        │
│ APP 签名（unidbg 常驻服务 / Xposed RPC）│◀────▶│  ├ Spider A（平台 A）          │
│ 设备身份池（自主注册）                  │ HTTP │  ├ Spider B（平台 B）          │
│ 解密逻辑（响应字段解析）                │      │  └ Spider C（平台 C）          │
└────────────────────────────────────────┘      └───────────┬────────────────────┘
                                                            │
                                                   ┌────────▼────────┐
                                                   │  Redis（共享）   │
                                                   │ 队列 / 去重 / 锁 │
                                                   └────────┬────────┘
                                                            │
                                                   ┌────────▼────────┐
                                                   │ Pipeline → 数仓 │
                                                   └─────────────────┘
```

**两条主线分离**：逆向侧只负责"让请求合法"，采集侧只负责"把数据拿全"。
两侧通过 HTTP 接口或 Node 服务解耦，任一侧升级不影响另一侧。

### 1.3 APP 侧：某X音 六神签名（重点）

#### 1.3.1 路线判定：先证明"纯算不可行"，再走仿真

**纪律：不许凭感觉判断，六条证据逐条跑、逐条贴输出。**

| # | 检查 | 命令 / 方法 | 判定阈值 |
|---|---|---|---|
| ① | crypto 常量扫描 | 扫 `libmetasec_ml.so` 的 MD5 T0 / SHA256 K0 / AES S-box / SM3 IV / Simon Z | **全部 0 命中** → 非常规实现 |
| ② | 签名锚点扫描 | `strings` 在各 so 里数 `x-gorgon`/`x-argus` 等出现次数 | 签名库 **0 处**，另一库 1 处 → **跨库** |
| ③ | 静态可达性 | adrp+add 全扫（掩码 `(w & 0x9F000000) == 0x90000000`） | 仅 1-2 处且只写字段 → **无有效锚点** |
| ④ | JIT 判定 | 运行时看签名计算 pc 所在内存映射 | 落在匿名可执行页 → **算法不在文件里** |
| ⑤ | JNI 依赖度 | verbose 日志统计回调种类 | **> 30 种** → 重写等于写半个仿真器 |
| ⑥ | 密钥来源 | 搜 32/64 位硬编码 hex；查 license/token 字段 | 无硬编码 key + 有 license → **key 不在本地** |

**实测结论（40.2.0）**：六条命中 5 条 → 纯算不可行，走 unidbg。

关键事实：

- 签名材料在 `libmetasec_ml.so`（4.5 MB），**组头逻辑在 `libsscronet.so`**，两库分离
- `libsscronet.so` 里 `x-gorgon` 唯一代码引用为一条 `adrp+add` 字符串赋值，追 4 层调用未到写入点
- license 为 244 字节 base64，与 appID 绑定，服务端签发

#### 1.3.2 unidbg 实现方案

**技术栈**：unidbg 0.9.10-SNAPSHOT + unicorn2 + JDK 21

**加载顺序（错一步静默失败）**：

```java
1. libc++_shared.so           // C++ 运行时先加载
2. 提前 resolveClass 声明目标库会 FindClass 的类
3. libmetasec_ml.so
4. callJNI_OnLoad
```

> 第 2 步是坑：native 在 `JNI_OnLoad` 里用 `FindClass → GetSuperClass → RegisterNatives`
> 定位注册类。类不存在时**不报错**，只是后续所有调用返回 null。

**JNI 桩三铁律**：

| 铁律 | 原因 |
|---|---|
| 未知 op 返回 null，不要"造"返回值 | 造错类型会让 native 走进意外分支 |
| 时间类回调返回真实时间 | 钉死时间戳会导致签名过期 |
| 路径类回调返回真实存在的目录 | 返回不存在路径会走首次启动分支 |

**驱动初始化链（op 表）**：

| op | 作用 | 返回 |
|---|---|---|
| `0x1000003` | Context 初始化 | 无 |
| `0x100000c` | 上下文配置 | 无 |
| `0x1000001` | 字符串解密（`bebb7f` → sdkVersion） | String |
| `0x5000001` | 库初始化 | Integer（0 = 成功） |
| `0x4000001` | **配置验证** | **必须 Boolean.TRUE** |
| `0x4000002` | 建立会话 | Long（handle，非 0） |
| `0x2000002` / `0x2000003` | 设 device_id / install_id | 无 |
| `0x2000006` | **取六神头** | String[] 键值对 |

> 注意：真机启动序列里**没有** `0x2000006`，走的是另一条生产路径。
> 但仿真调 `0x2000006` 产出的头**服务端接受**——不要因为"真机不调用"就放弃这个 op。

**三条工程铁律**：

| 铁律 | 现象 | 处理 |
|---|---|---|
| **JNI 环境线程绑定** | 跨线程报 `NullPointerException: Unpointer.toIntPeer()` | 每实例一条专属线程，构造与调用都在该线程 |
| **初始化失败是粘性的** | 同代码 6 次成功 2 次；失败后重试无效 | 探针验证 + **重建整个 emulator**（实测 15 次内必成功） |
| **设备身份与请求参数同源** | 签名用 A 设备、参数用 B 设备 → 服务端拒绝 | 同一实例绑定同一身份，池化时成组租借 |

**性能基准**：

| 指标 | 值 |
|---|---|
| 单次签名 | 48 ms（37-68 ms） |
| 单页采集（签名 + 请求） | 约 550 ms |
| 每实例内存 | 约 120 MB |
| 6 实例预热 | 约 40 秒 |
| 12 实例预热 | 120-150 秒 |

#### 1.3.4 设备身份：自主注册（脱离真机的关键）

没有真实设备 ID，仿真是跑不起来的（会触发 `svc` 直接退出）。所以必须能自己造设备。

**注册链路**：

```
POST https://log.snssdk.com/service/2/device_register/
Header: 39 个字段（含 magic_tag: ss_app_log、sig_hash、设备指纹）
Body:   TTEncrypt(GZIP(设备指纹 JSON))
返回:   device_id / install_id / cdid / device_token
```

| 环节 | 关键点 |
|---|---|
| TTEncrypt | `libEncryptor.so`，类 `com/bytedance/frameworks/encryptor/EncryptorUtil`，方法 `ttEncrypt([BI)[B` |
| **第二参数** | 是**数据长度**，不是 flag。填 1 会得到 `device_id: 0`（输出恒 118 字节） |
| 输出格式 | `74 63 05 10 00 00` + 32 字节 seed + 密文 |
| 设备画像 | 19 套真实画像（品牌↔型号↔OS↔分辨率↔DPI↔ROM↔渠道 必须自洽） |
| sig_hash | 填错不报错，但设备会被降权 |

**实测**：注册成功率 100%，返回的 device_id 可直接用于评论采集，全程不碰手机。

#### 1.3.5 签名服务接口契约

**对外形态**：HTTP 接口（对应架构图"逆向产出接口/Node 服务"）

```
GET  /api/sign?url=<待签 URL>&op2=0
     → { ok, headers: { X-Argus, X-Gorgon, X-Helios, X-Khronos, X-Ladon, X-Medusa } }

GET  /api/comments?aweme_id=<id>&cursor=0&count=50
     → { ok, page: { cursor, raw } }

POST /api/register
     → { ok, device: { device_id, install_id, cdid, device_token } }

GET  /api/health
     → { status, instances, idle, signed, failed, softBlocks, pausedDevices }
```

**关键设计**：

| 设计点 | 说明 |
|---|---|
| 池化 | N 个实例，每个绑定一台设备身份，**成组租借** |
| 按设备冷却 | 某台设备被限流只冷却它，不能全局封（见 §2.7） |
| 健康检查 | 暴露 `pausedDevices`，采集侧据此降速 |
| 重试 | 初始化失败自动重建，对外表现为偶发 5xx |

#### 1.3.6 验收标准（三层，缺一不可）

| 层 | 判据 |
|---|---|
| ① HTTP | `200` |
| ② 业务码 | `status_code == 0` |
| ③ 数据 | 返回体**非空**且结构符合预期 |

**只满足 ① 一律视为未验证。** 三种常见假象：

| 假象 | 真相 |
|---|---|
| `200` + `status_code = -99999` | **请求参数不全**（不是签名错）。真机带 28 个参数，只发 8 个必挂 |
| `200` + `status_code = 0` + 空列表 | **软封禁**，看起来完全正常 |
| `200` + 成功码 + 旧数据 | 服务端缓存 |

## 2. 采集架构

### 2.1 总体

```
逆向产出（接口 / Node 服务）
        │ HTTP
        ▼
Scrapy 进程 × N（独立运行，互不干预）
        │
        ├─ 共享 Redis：队列 / 去重指纹 / 分布式锁
        │
        └─ Pipeline → 数仓
```

**同一平台的不同采集任务按 Spider 拆分，而不是拆集群。**
每个 Spider 有唯一 `name`，Scrapy-Redis 按 `spider name` 自动隔离请求队列与去重指纹，
多进程共享 Redis 但任务数据互不冲突。

`SCHEDULER_PERSIST = true` 保证断点续爬与跨实例调度一致性，避免实例退出后调度器清空导致重复调度。

### 2.2 签名能力接入方式

| 方式 | 适用 | 优缺点 |
|---|---|---|
| HTTP 接口 | APP 侧（六神、Shield） | 解耦、可多语言调用；多一次网络往返 |
| Node 服务 | TT / YT（依赖 JS 环境） | 保留原始 JS 运行时；需 Node 进程常驻 |
| 进程内调用 | Ins / AMZ（纯 Python） | 零开销；升级要重启采集进程 |

**推荐**：APP 侧一律走 HTTP，Web 侧能纯 Python 的走进程内，依赖 JS 的走 Node。

### 2.3 分布式锁的正确用法

业务层用 Redis 分布式锁保证**目标级互斥**，防止多进程对同一目标的 token/cookie 刷新冲突。

**六神路线多一个锁场景**：设备租借。

| 资源 | 为什么要锁 |
|---|---|
| 目标（账号/话题） | token/cookie 刷新不可并发 |
| **设备身份** | 同一 device_id 被两个进程同时用 → 直接触发限流 |

设备租借的锁粒度：

```
LOCK device:<device_id>  TTL=30s
持有者：一个采集进程处理一批页面期间
冲突处理：拿不到锁 → 换下一台设备（不是等待）
```

### 2.4 中间件分层

| 中间件 | 职责 |
|---|---|
| 下载中间件 | UA 池轮换、代理池按需获取与失效剔除、重试、`curl_cffi` 指纹伪造 |
| Spider 中间件 | 签名注入（调 HTTP 签名服务）、参数拼装、响应解密 |
| Pipeline | 字段解析（复用逆向产出的解密逻辑）、去重、分流入库 |

### 2.5 限流与配额模型（六神实测，其他平台同理）

**这一节是整个系统的性能天花板，必须按实测数据设计，不能拍脑袋。**

#### 结论一：限流按设备，不按 IP

A/B 对照实验（唯一变量是设备数）：

| 设备数 | 并发 | 成功 | 服务端软封 | 墙钟 |
|---|---|---|---|---|
| 1 台 | 20 | 15/20 | **5 次** | 21.4 s |
| 5 台 | 20 | **20/20** | **0 次** | 4.9 s |
| 1 台 | 40 | 22/40 | **23 次** | 31.8 s |
| 5 台 | 40 | **39/40** | **0 次** | 10.9 s |

补充证据：池内 6 台设备全部冷却（`pauseMs=104s`）时，一台刚注册的新设备**一次请求就通**。

#### 结论二：单设备窗口预算约 15-20 请求

超出后该设备进入冷却（1-2 分钟）。冷却**必须按设备做**：

> 踩过的坑：把软封做成全局闸门，结果一次空响应封住整个池 ——
> 12 台全新设备跑 150 页，只发出 12 个请求，其余 138 个被本地秒拒。

正确处理：

| 事件 | 反应 |
|---|---|
| 浅 cursor（< 2000）返回空 | 只冷却**这台设备** 90 秒，换一台重试 |
| 深 cursor（≥ 2000）返回空 | 视为可见深度到底，正常返回，不冷却 |
| HTML `Access Denied` | 全局短暂冷却（罕见） |

#### 结论三：页数与设备数的配比

```
设备数 ≈ 页数 / 12
```

端到端实测：

| 配置 | 结果 |
|---|---|
| 6 台 / 150 页 | 120 OK + 30 被限，5655 条，31 s，软封 6 次 |
| **12 台 / 150 页** | **148 OK + 2 深 cursor 空，7070 条，19.9 s，软封 0 次** |

#### 结论四：服务端有可见深度上限

单个视频约 7000-7400 条评论可见，再往后返回空（`total` 字段会回显 cursor）。
**这是硬限制，加设备、换代理都突破不了。**

### 2.6 断点续爬

| 层 | 机制 |
|---|---|
| 调度 | `SCHEDULER_PERSIST = true` |
| 去重 | Scrapy-Redis `dupefilter`，按 spider name 隔离 |
| 页级 | 客户端每页落盘 `*.parts.jsonl`，中断后 `--resume` 从断点继续 |
| 失败重试 | 单页 3 次，失败后**换设备**（不是原地重试） |

## 3. 反检测分层

| 层 | 手段 |
|---|---|
| **网络层** | 自建动态住宅代理池，每请求换 IP 并限频；`curl_cffi` 伪造 TLS/JA3 指纹 |
| **请求层** | 请求头随机化，UA/分辨率/时区与设备画像自洽 |
| **设备层** | **设备身份池**（六神路线核心）：19 套真实画像，自主注册，按需扩充 |
| **页面层** | 处理反调试、前端加密入口定位；浏览器渲染仅用于登录态获取，不进主链路 |

### 3.1 设备层要点（六神经验）

| 要点 | 说明 |
|---|---|
| 画像必须自洽 | 品牌↔型号↔OS 版本↔分辨率↔DPI↔ROM↔渠道，任何一项矛盾都会被降权 |
| 一设备一实例 | 签名实例与设备身份绑定，不能混用 |
| 冷却隔离 | 单设备冷却不影响其他设备 |
| 容量规划 | 每设备 ~15-20 请求/窗口；按目标页数反推设备数 |
| 存活观察 | 新注册设备可用，但长期存活率需持续观察（当前未量化） |

## 4. 交付

### 4.1 最小可执行原则

| 档位 | 形态 | 什么时候才用 |
|---|---|---|
| A. CLI | 1 核心类 + 1 main | 验证可行性、几十次调用 |
| B. RPC | Xposed 模块 + 客户端 | 有 root 手机、当天要结果 |
| C1. 常驻单实例 | 1 controller + 1 service | 连续调用 > 50 次 |
| C2. C1 + 实例池 | + 1 个 Pool 类 | 并发 > 1、需设备轮换 |
| C3. C2 + 注册/限流 | + 2 个 service | 需自动造设备、失败率 > 10% |

**先做 A 或 C1，验证通过再按触发器升级，禁止跳档。**

### 4.2 数据 schema（评论为例）


## 5. 风险与边界（必须向使用方说明）

| 风险 | 现状 | 应对 |
|---|---|---|
| **算法未还原** | 六神走仿真，算法仍在 so 里 | 不追求还原；把 so 当黑盒，稳定调用即可 |
| **深度上限** | 单视频约 7000 条可见（占比 54%） | 提前告知数据完整度；不做无效优化 |
| **版本漂移** | 偏移/配置/license 全部版本绑定 | 建立换版本适配清单（8 项），预留 0.5-1 天 |
| **设备存活** | 注册即用，长期未量化 | 建立设备池健康度监控，按失败率淘汰补充 |
| **加固升级** | 目标升到 VMP+JIT 后纯算彻底不可行 | 仿真路线天然免疫，但需重新适配 op 表 |

## 6. 落地顺序建议

| 阶段 | 内容 | 产出 |
|---|---|---|
| P0 | 六神签名跑通（unidbg CLI） | 能出 6 个头，真实请求 `status_code=0` |
| P0 | 设备自主注册 | 不依赖真机能造设备 |
| P1 | 常驻签名服务（C2） | HTTP 接口，12 实例 |
| P1 | 采集接入（单 Spider） | 150 页 / 20 秒 / 7070 条 |
| P2 | 设备池 + 按设备冷却 | 连续跑不触发全局限流 |
| P2 | 多 Spider + Redis 锁 | 多目标并行互不干扰 |
| P3 | 其他平台接入 | TT / YT / Ins / AMZ / 某X书 |

## 附：核心认知（写死在最前面）

1. **签名不是难点，抓取调度才是。** 六神签名 48ms、100% 成功；真正的天花板是设备配额和可见深度。
2. **限流按设备，不按 IP。** 所以设备池是核心资产，代理只是补充。
3. **"签名能出" ≠ "服务端接受"。** 验收必须打到真实请求，看业务码和数据。
4. **算法还原的投入产出比在 VMP+JIT 面前极低。** 把 so 当黑盒仿真，比读懂它便宜一个数量级。
